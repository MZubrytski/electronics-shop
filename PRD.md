# PRD — интернет-магазин электроники

**Статус:** черновик v1
**Автор:** Максим Зубрицкий
**Обновлено:** 07.08.2026

> Интерфейс магазина — **только английский**, валюта — **только USD**.
> Идентификаторы (роли, статусы, названия способов доставки) в документе оставлены
> на английском: это значения в коде и в базе, а не текст для перевода.

---

## 1. О проекте

Полнофункциональный интернет-магазин потребительской электроники: ноутбуки,
смартфоны, наушники, мониторы и аксессуары.

Проект делается для портфолио. Задача — показать законченное развёрнутое приложение
production-образца, а не обслуживать реальный бизнес. При этом каждое решение
принимается так, как если бы магазин был настоящим.

### Цели

| № | Цель | Чем проверяется |
| --- | --- | --- |
| Ц1 | Посетитель находит товар и доводит покупку до конца | Полный заказ тестовой картой Stripe |
| Ц2 | Три роли с действительно разными правами | Демо-аккаунты user / admin / super admin |
| Ц3 | Карточки товаров индексируются и красиво расшариваются | HTML с сервера + OG-теги |
| Ц4 | Ключевые бизнес-правила покрыты тестами | Деньги, склад, права доступа |
| Ц5 | Ревьюер запускает проект локально одной командой | `docker compose up && npm run dev` |

### Чего в v1 не будет

Записано явно, чтобы не расползлось по ходу дела:

- маркетплейс и несколько продавцов;
- варианты товара (цвет, объём памяти) — каждая конфигурация отдельный товар;
- несколько языков и валют — **только английский и USD**;
- промокоды, акции, программы лояльности;
- транзакционные письма (подтверждение заказа, восстановление пароля по почте);
- интеграция с реальными службами доставки и валидация адресов;
- возвраты и отмены заказов покупателем;
- сравнение товаров;
- realtime (живые остатки, чат).

## 2. Пользователи и роли

### Кто пользуется

| Роль | Что ему нужно |
| --- | --- |
| **Гость** (не вошёл) | Посмотреть каталог, найти товар, положить в корзину, решиться на покупку |
| **Покупатель** (`user`) | Купить, следить за своими заказами, вести wishlist, писать отзывы |
| **Менеджер** (`admin`) | Видеть состояние бизнеса, обрабатывать заказы, следить за остатками |
| **Владелец** (`super_admin`) | Всё то же плюс управление каталогом и сотрудниками |

### Матрица прав

`—` — нет доступа, `Ч` — чтение, `З` — создание и изменение.

| Возможность | Гость | user | admin | super_admin |
| --- | :---: | :---: | :---: | :---: |
| Каталог, поиск, карточка товара | Ч | Ч | Ч | Ч |
| Корзина: добавить, изменить, удалить | ✓ | ✓ | ✓ | ✓ |
| Перейти к оплате | — | ✓ | ✓ | ✓ |
| История своих заказов | — | Ч | Ч | Ч |
| Wishlist | — | ✓ | ✓ | ✓ |
| Написать отзыв | — | ✓ | ✓ | ✓ |
| Изменить или удалить **свой** отзыв | — | ✓ | ✓ | ✓ |
| Удалить **любой** отзыв | — | — | — | ✓ |
| Дашборд: выручка, топ товаров | — | — | Ч | Ч |
| Список всех заказов, смена статуса | — | — | З | З |
| Остатки на складе (просмотр) | — | — | Ч | Ч |
| **Создание, изменение, удаление товаров** | — | — | — | З |
| **Загрузка изображений товаров** | — | — | — | З |
| Изменение остатка вручную | — | — | — | З |
| Список пользователей, смена ролей | — | — | — | З |

> **Почему разделены `admin` и `super_admin`.** Это не формальность: разделение
> превращает RBAC из одного `if (role === 'admin')` в настоящую авторизацию с
> правилами на уровне ресурса. `admin` ведёт магазин каждый день, `super_admin`
> владеет каталогом и сотрудниками. Один и тот же отзыв может удалить его автор
> или `super_admin`, но не `admin` — вот это уже интересно объяснять на собеседовании.

### Правила входа

- Просмотр каталога и корзина работают **без аккаунта**.
- Нажатие **Proceed to checkout** требует входа. Гостя уводит на страницу входа
  и после успеха возвращает обратно в оформление.
- При входе **корзина гостя сливается** с корзиной аккаунта (см. §7.3).
- Сессии — JWT в **httpOnly-куках** (см. §9.1).

## 3. Технологии

| Слой | Выбор | Почему |
| --- | --- | --- |
| Монорепозиторий | npm workspaces | Два приложения и один общий пакет — большего не нужно |
| Витрина | **Nuxt 4** (SSR) | Индексация и превью ссылок на карточки товаров |
| Админка | Тот же Nuxt, `routeRules: { '/admin/**': { ssr: false } }` | За логином, SSR там ничего не даёт |
| UI | **Nuxt UI** (Tailwind + Reka UI) | `UTable` на TanStack, `UForm` с валидацией теми же zod-схемами, что в `contracts` |
| API | **NestJS** | Модули, DI, guard'ы — настоящий бэкенд |
| База | **PostgreSQL** | |
| ORM | **Prisma** | Типобезопасные запросы, миграции |
| Контракты | **zod** в `packages/contracts` | Одна схема → валидация на API, типы на фронте и проверка форм в `UForm` |
| Авторизация | JWT (access + refresh) в httpOnly-куках | Совместимо с SSR |
| Оплата | **Stripe Elements** + вебхуки | Форма карты остаётся на нашем checkout |
| Изображения | **Cloudinary** | Загрузка из админки, трансформации на лету |
| Тесты | Vitest, @testing-library/vue, Supertest | |

## 5. Функциональные требования — витрина

### 5.1 Каталог

- Сетка карточек: фото, название, бренд, цена, рейтинг, метка наличия.
- **Поиск** по названию и бренду, без учёта регистра, подстрокой (`ILIKE`).
- **Фильтры:** категория, бренд (множественный выбор), диапазон цены,
  «только в наличии».
- **Сортировка:** по релевантности (по умолчанию), цена ↑, цена ↓, рейтинг, новизна.
- **Пагинация:** 24 товара на страницу, по смещению.
- Состояние фильтров живёт **в query-параметрах URL** — ссылку должно быть можно
  переслать, а перезагрузка не должна сбрасывать выбор.
- Пустая выдача показывает сообщение и кнопку сброса фильтров.

### 5.2 Карточка товара

- Галерея изображений: `UCarousel` с полосой миниатюр, от одного до пяти фото.
- Название, бренд, цена, средний рейтинг, количество отзывов.
  Звёзды рейтинга — свой маленький компонент на `UIcon`: готового в Nuxt UI нет.
- Наличие: `In stock` / `Only N left` (при N ≤ 5) / `Out of stock`.
- Таблица характеристик из JSONB-поля `specs`.
- Добавление в корзину со счётчиком количества, ограниченным остатком.
- Добавление в wishlist (нужен вход; гостю предлагается войти).
- Список отзывов с пагинацией и форма отзыва для вошедших.
- **SEO:** уникальные `<title>` и meta description, OG-теги, JSON-LD типа `Product`
  с ценой и наличием, канонический URL.

### 5.3 Корзина

- Доступна всем, включая гостей.
- Строка: фото, название, цена за штуку, счётчик, сумма строки, удаление.
- Итоги: сумма товаров, доставка, итог заказа.
- Количество ограничено текущим остатком. Если остаток упал ниже количества
  в корзине, строка подсвечивается, а количество обрезается при следующей
  синхронизации с сервером.
- Корзина гостя хранится в куке (список id и количеств) и **перепроверяется на
  сервере** при каждой загрузке страницы: цены и остатки всегда берутся из базы,
  а не из куки.

### 5.4 Wishlist

- Нужен вход.
- Иконка-сердце на карточках каталога и на странице товара.
- Отдельная страница со списком и кнопкой «перенести в корзину».

### 5.5 Оформление заказа

Одна страница, три блока:

1. **Адрес доставки** — имя, страна, город, адрес, индекс, телефон.
   Вошедшим пользователям подставляется сохранённый адрес.
2. **Способ доставки:**

   | Способ | Срок | Цена |
   | --- | --- | --- |
   | Standard | 5–7 рабочих дней | $9.99, **бесплатно от $500** |
   | Express | 1–2 рабочих дня | $24.99 |

3. **Оплата** — форма карты Stripe Elements.

- Блок с итогами прилипающий, пересчитывается при смене способа доставки.
- Ошибки валидации показываются под полем и только после того, как поле трогали.
- Уход со страницы с частично заполненной формой спрашивает подтверждение.

### 5.6 Поток оплаты

```
1. Клиент  → POST /orders            создаём заказ, статус pending_payment
                                     остаток резервируется атомарно (§9.2)
2. Сервер  → Stripe                  создаём PaymentIntent(сумма, currency: usd)
3. Сервер  → Клиент                  отдаём clientSecret
4. Клиент  → Stripe                  confirmPayment() через Elements
5. Stripe  → Сервер                  вебхук payment_intent.succeeded
6. Сервер                            статус paid, резерв подтверждён
```

- Страница успеха **опрашивает заказ**, пока он не станет `paid`: вебхук может
  прийти позже, чем пользователя вернёт на сайт.
- Если за 60 секунд вебхук не пришёл, показывается «Payment is being processed»
  и ссылка на историю заказов.
- Обработчик вебхуков обязан **проверять подпись** и быть **идемпотентным**:
  Stripe доставляет событие несколько раз, и применить его дважды нельзя.
- `payment_intent.payment_failed` → статус `payment_failed`, резерв возвращается
  на склад.
- Заказ, зависший в `pending_payment` дольше **30 минут**, отменяется фоновой
  задачей: статус `cancelled`, зарезервированный остаток возвращается на склад.

### 5.7 Заказы

Статусы:

```
pending_payment → paid → shipped → delivered
       ↓            ↓
payment_failed   cancelled
```

- Покупатель видит: номер, дату, состав, суммы, способ доставки, адрес и статус
  в виде таймлайна.
- Для покупателя заказ неизменяем: ни редактирования, ни отмены в v1.

### 5.8 Отзывы

- Отзыв может оставить **любой вошедший пользователь на любой товар** —
  покупка не требуется, модерации нет.
- Один отзыв на пару «пользователь + товар»; повторная попытка редактирует
  существующий.
- Поля: оценка 1–5 (обязательно), текст до 2000 символов (необязательно).
- Автор может изменить и удалить свой отзыв. `super_admin` может удалить любой.
- Рейтинг товара — среднее по отзывам, округлённое до одного знака.

## 6. Функциональные требования — админка

### 6.1 Дашборд (`admin` и выше)

- Ряд показателей: выручка за период, число заказов, средний чек, новые покупатели.
- Переключатель периода: 7 / 30 / 90 дней.
- **График выручки** по дням за выбранный период.
- **Топ-10 товаров** по выручке: название, продано штук, выручка.
- **Последние 5 отзывов**: оценка, товар, начало текста, ссылка на карточку.
- **Заканчивается на складе**: товары с остатком ≤ 5.

Все цифры считаются по заказам в статусах `paid`, `shipped` и `delivered`.
`pending_payment` и `cancelled` в расчёт не входят.

### 6.2 Заказы (`admin` и выше)

- `UTable` (TanStack Table внутри) с серверной пагинацией, сортировкой и фильтрацией.
- Фильтры: статус, диапазон дат, поиск по номеру заказа и email покупателя.
- Смена статуса выпадающим списком, только по разрешённым переходам
  (`paid → shipped → delivered`, `pending_payment → cancelled`).
- Страница заказа: состав, покупатель, адрес, способ доставки, id платежа,
  история смены статусов.

### 6.3 Остатки (`admin` — чтение, `super_admin` — запись)

- Таблица товаров с текущим остатком, сортировкой и фильтром «заканчивается».
- `super_admin` правит остаток прямо в строке; `admin` видит колонку только
  на чтение.

### 6.4 Каталог (только `super_admin`)

- Список товаров с поиском и пагинацией.
- Форма создания и редактирования: название, slug, категория, бренд, цена, остаток,
  описание, характеристики (редактор пар «ключ — значение»), изображения.
- **Загрузка изображений в Cloudinary** через подписанный запрос от API;
  в базе хранится `public_id`, трансформации применяются при чтении.
- До пяти изображений, порядок меняется перетаскиванием, первое — обложка.
- Удаление — **мягкое** (`deletedAt`): товар, на который ссылается прошлый заказ,
  не должен исчезать из истории.

### 6.5 Пользователи (только `super_admin`)

- Список: email, имя, роль, дата регистрации, число заказов.
- Смена роли между `user`, `admin`, `super_admin`.
- `super_admin` не может понизить сам себя — защита от ситуации, когда в системе
  не осталось ни одного владельца.

## 7. Модель данных

```
User            id, email(uniq), passwordHash, name, role, createdAt
Address         id, userId, fullName, country, city, line1, postalCode, phone, isDefault

Category        id, slug(uniq), title, sortOrder
Brand           id, slug(uniq), title

Product         id, slug(uniq), title, description,
                categoryId, brandId,
                priceCents(int), stock(int),
                specs(jsonb),
                ratingAvg(decimal), reviewCount(int),
                createdAt, deletedAt(nullable)
ProductImage    id, productId, cloudinaryPublicId, position

Cart            id, userId(nullable), createdAt
CartItem        id, cartId, productId, quantity

WishlistItem    id, userId, productId, createdAt      uniq(userId, productId)

Order           id, orderNumber(uniq, формат ORD-2026-000123), userId,
                status, subtotalCents, shippingCents, totalCents,
                shippingMethod, shippingAddress(jsonb — снимок),
                stripePaymentIntentId, createdAt, paidAt
OrderItem       id, orderId, productId,
                titleSnapshot, priceCentsSnapshot, quantity

Review          id, productId, userId, rating(1..5), text, createdAt, updatedAt
                uniq(productId, userId)

ProcessedWebhook  stripeEventId(uniq), processedAt
RefreshToken      id, userId, tokenHash, expiresAt, revokedAt
```

### Решения по модели

**7.1 Деньги хранятся в целых центах.** `priceCents`, `totalCents`. Никаких дробных
чисел: `0.1 + 0.2 !== 0.3`, и на заказе из десяти позиций итог разъезжается на цент.
Форматирование в `$1,299.00` происходит только на уровне отображения.

**7.2 В позициях заказа лежат снимки.** `titleSnapshot` и `priceCentsSnapshot`
копируются в момент оформления. Если завтра цена изменится, старый заказ обязан
показывать то, что человек реально заплатил. То же самое с адресом — он хранится
JSONB-снимком, а не ссылкой на `Address`.

**7.3 Слияние корзин при входе.** Корзина гостя живёт в куке. При входе для каждой
её строки: если товар уже есть в корзине аккаунта — количества складываются и
обрезаются по остатку; если нет — строка добавляется. Затем кука очищается.

**7.4 Характеристики в JSONB.** У ноутбука процессор и диагональ, у наушников —
тип излучателя: колонку под каждую характеристику не заведёшь. `specs` хранит
`{ "CPU": "M3 Pro", "RAM": "18 GB" }` и выводится таблицей на карточке.
Фильтрация по характеристикам в v1 **не нужна**, поэтому GIN-индекс пока не заводим.

**7.5 Мягкое удаление товаров.** Товар, на который ссылается заказ, физически
не удаляется. Все запросы каталога фильтруют `deletedAt IS NULL`.

## 8. Демо-данные

Демо должно выглядеть как настоящий магазин, а не как тестовая заглушка.

- **5 категорий:** Laptops, Smartphones, Headphones, Monitors, Accessories.
- **10–12 брендов:** Apple, ASUS, Lenovo, Samsung, Sony, LG, Logitech и т. д.
- **60–80 товаров** с правдоподобными названиями, ценами, описаниями и
  характеристиками; фото заранее загружены в Cloudinary.
- **~150 отзывов**, распределённых по товарам, с перекосом оценок в сторону 4–5,
  как в жизни.
- **~40 заказов** за последние 90 дней в разных статусах — иначе графики на
  дашборде пустые и бессмысленные.
- **Три демо-аккаунта**, доступы опубликованы в README:

  | Email | Пароль | Роль |
  | --- | --- | --- |
  | `customer@demo.shop` | `demo1234` | user |
  | `manager@demo.shop` | `demo1234` | admin |
  | `owner@demo.shop` | `demo1234` | super_admin |

- У нескольких товаров специально стоит `stock = 0` и `stock = 1` — чтобы состояние
  «нет в наличии» и гонка за последним товаром были воспроизводимы.

## 9. Ключевые технические решения

### 9.1 JWT в httpOnly-куках, а не в localStorage

Nuxt рисует страницы на сервере, а сервер не может прочитать `localStorage`.
Если держать токен там, каждая персональная страница либо теряет SSR, либо мигает
неавторизованным состоянием.

Поэтому:

- access-токен (15 минут) и refresh-токен (30 дней) лежат в куках с флагами
  `httpOnly`, `Secure`, `SameSite=Lax`;
- браузерный JavaScript вообще не касается токена — это заодно убирает целый класс
  краж токена через XSS;
- серверные маршруты Nuxt (`server/api/*`) работают тонкой прослойкой: подставляют
  куку и ходят в NestJS;
- refresh-токены хранятся хешированными и **ротируются** при каждом использовании;
  повторное использование одного токена отзывает всю его цепочку.

### 9.2 Последний товар на складе — центральная техническая задача

Двое покупателей одновременно берут последнюю единицу. Наивная последовательность
«прочитал остаток → проверил → создал заказ» продаст обе: оба чтения увидят
`stock = 1`.

Требование: **остаток списывается атомарно при создании заказа**, внутри транзакции,
условным обновлением:

```sql
UPDATE products
   SET stock = stock - $qty
 WHERE id = $id AND stock >= $qty
```

Если обновлено ноль строк — заказ отклоняется с `409 Conflict` и понятным
сообщением. Если оплата затем провалилась или заказ отменён — остаток возвращается.

**Это должно быть доказано тестом:** 20 параллельных запросов на товар с
`stock = 1` дают ровно один успешный заказ и 19 отказов.

### 9.3 Идемпотентность вебхуков

Stripe доставляет одно и то же событие несколько раз — это его штатное поведение.
Применить `payment_intent.succeeded` дважды означает дважды пометить заказ
оплаченным и испортить график выручки.

`stripeEventId` записывается в `ProcessedWebhook` с уникальным ограничением
**в той же транзакции**, что и обновление заказа. Повторное событие упирается
в ограничение и пропускается с ответом `200 OK`, чтобы Stripe не повторял доставку.

### 9.4 Контракты как единственный источник правды

В `packages/contracts` лежат zod-схемы. NestJS валидирует ими входящие запросы,
Nuxt выводит из них TypeScript-типы. Переименованное поле ломает сборку фронта
сразу, а не падает в рантайме у пользователя.

Модели Prisma **не** экспортируются на фронт: модель базы и ответ API — разные вещи.
`passwordHash` есть в первой и не должен появиться во второй никогда.

## 10. Нефункциональные требования

### SEO
- Серверный рендеринг для `/`, `/catalog`, `/product/:slug`.
- Уникальные title и description на каждый товар, OG-теги с обложкой.
- JSON-LD типа `Product` с `price`, `priceCurrency: USD`, `availability`.
- `sitemap.xml`, генерируемый из каталога, и `robots.txt`.

### Производительность
- Lighthouse ≥ 90 на карточке товара (мобильный профиль).
- Изображения через Cloudinary: WebP/AVIF, нужные размеры, `loading="lazy"`
  для всего, что ниже первого экрана.
- Индексы на `categoryId`, `brandId`, `priceCents` для запросов каталога.

### Доступность
- Каталог, корзина и оформление проходятся с клавиатуры.
- У всех полей есть подписи, ошибки связаны через `aria-describedby`.
- Видимое кольцо фокуса, контраст не ниже 4.5:1.

### Безопасность
- Пароли хешируются argon2.
- Ограничение частоты на `/auth/*` — 10 попыток в минуту с одного IP.
- Подпись вебхука Stripe проверяется; в остальном эндпоинт публичный.
- Каждый изменяющий эндпоинт админки закрыт проверкой роли **и** проверкой
  владения ресурсом там, где это применимо.
- Загрузка в Cloudinary подписывается на сервере, секрет в браузер не попадает.

### Тесты

| Уровень | Что покрывает |
| --- | --- |
| Модульные | форматирование денег, итоги корзины, правила доставки, переходы статусов, проверки прав |
| Интеграционные (Supertest) | вход и обновление токена, создание заказа, **гонка за остатком**, идемпотентность вебхука |
| Компонентные (Testing Library) | фильтры каталога, корзина, валидация формы оформления |

Процент покрытия целью не является. Целью являются перечисленные случаи.

## 13. Принятые решения

Вопросы, которые оставались открытыми на момент черновика. Все закрыты 07.08.2026.

| Вопрос | Решение |
| --- | --- |
| Отмена заказа покупателем | **Не делаем в v1.** Заказ для покупателя неизменяем |
| Таймаут резерва остатка | **30 минут** фоновой задачей, затем `cancelled` и возврат на склад |
| Вложенность категорий | **Плоский список**, один уровень |
| Транзакционные письма | **Не делаем**, ни в каком виде |
| Формат номера заказа | **`ORD-2026-000123`** — префикс, год, сквозной шестизначный номер внутри года |

### Что следует из решения про таймаут

Появляется единственная фоновая задача в проекте. Реализация — `@nestjs/schedule`,
запуск раз в 5 минут:

```
найти заказы: status = pending_payment AND createdAt < now() - 30 min
для каждого в транзакции:
    вернуть остатки по позициям заказа
    status = cancelled
```

Задача должна быть **идемпотентной** и безопасной при параллельном запуске
(если однажды появится второй экземпляр API): статус меняется условным
обновлением `WHERE status = 'pending_payment'`, и если обновлено ноль строк —
заказ уже обработан, остатки не возвращаем повторно.

Это тот же приём, что и в §9.2, и тестируется так же.

### Что следует из формата номера

Сквозная нумерация внутри года требует счётчика, устойчивого к параллельным
заказам. Простейший надёжный вариант — отдельная последовательность в Postgres:

```sql
CREATE SEQUENCE order_number_seq_2026 START 1;
```

Номер собирается как `ORD-2026-` + `nextval` с дополнением нулями до шести знаков.
Брать `COUNT(*) + 1` нельзя: два одновременных заказа получат одинаковый номер.
