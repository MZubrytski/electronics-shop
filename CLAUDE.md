# electronics-shop

Учебный интернет-магазин электроники для портфолио. Монорепозиторий на npm workspaces.

Отвечать и писать документацию **по-русски**. Весь текст в интерфейсе, названия
переменных, коммиты и комментарии в коде — **по-английски**. Валюта только USD.

## Документацию обновляем в том же изменении, что и код

Документация — часть задачи, а не уборка после неё. Меняешь структуру или
поведение — правь соответствующий файл **сразу**, до того как считать работу
законченной. Отдельного «потом обновлю доки» не бывает: расхождение обнаружится
через месяц, и разбираться будет уже некому.

Что где отражается:

| Изменение                                        | Что обязательно обновить                                                 |
| ------------------------------------------------ | ------------------------------------------------------------------------ |
| Новый воркспейс, переименование, перенос папок   | «Структура» в этом файле + `workspaces` в корневом `package.json`        |
| Новый или переименованный скрипт `npm`           | «Команды» в этом файле                                                   |
| Новый маршрут или страница                       | Карта страниц — PRD §4                                                   |
| Новый или изменённый эндпоинт                    | PRD §5–6 **и** схема в `packages/contracts`                              |
| Изменение модели данных, новая таблица или поле  | PRD §7 + миграция Prisma                                                 |
| **Новая переменная окружения**                   | `.env.example` нужного приложения + таблица переменных в его `CLAUDE.md` |
| Переменная нужна на проде                        | ещё и docs/DEPLOY.md                                                     |
| Палитра, шрифт, сетка, состояния списков         | docs/DESIGN.md                                                           |
| Шаги CI, версия Node, новый инструмент сборки    | «CI» в этом файле + docs/SETUP.md                                        |
| Порядок сборки, новая зависимость между пакетами | «Порядок сборки» в этом файле                                            |
| Установлен или удалён скил                       | `skills-lock.json` + «Установленные скилы» в этом файле                  |
| Изменился процесс деплоя                         | docs/DEPLOY.md                                                           |
| **Начат новый этап**                             | план фичи в `docs/features/` + согласование **до** первой правки кода    |
| **Закончен любой шаг реализации**                | отметить `[x]` в docs/PLAN.md **в том же изменении**                     |
| Решение разошлось с планом фичи                  | правится план фичи, а не только код                                      |
| Появилась работа, которой в плане нет            | дописать пункт в нужный этап docs/PLAN.md                                |

Отдельно про три файла:

- **docs/PRD.md** — источник правды по продукту. Если реализация от него
  отходит, сначала меняется PRD, потом код. Не наоборот.
- **docs/PLAN.md** — рабочий чек-лист: что из PRD уже сделано и что осталось.
  Отмечается по ходу работы, а не задним числом (см. «План реализации» ниже).
- **docs/SETUP.md** — история сборки с нуля. Правится только тогда, когда
  изменение затронуло бы человека, поднимающего проект впервые: новый
  воркспейс, новая обязательная переменная, другая версия инструмента.
  Обычные фичи туда не дописываются.

Затронул структуру папок в `apps/api` или `apps/web` — проверь и `CLAUDE.md`
этого приложения тоже: там описаны раскладка каталогов и переменные окружения.

## План реализации

[docs/PLAN.md](docs/PLAN.md) — пошаговый план всего проекта по этапам F0–F12
из PRD §12. Это рабочий чек-лист, а не справка: он должен в любой момент честно
отвечать на вопрос «что уже сделано и что осталось» без чтения кода.

**Перед началом работы** — свериться с планом: какой этап идёт, какой пункт
следующий. Дальше — не сразу код, а фаза подготовки из раздела
«[Порядок работы над фичей](#порядок-работы-над-фичей)» ниже.
**После работы** — отметить сделанное.

План нарезан **фича за фичей, а не слой за слоем**: у каждого этапа своя миграция,
свои схемы, свои эндпоинты, свои страницы и строка «Можно потрогать» — то, что
открывается в браузере, когда этап закончен. Схему базы целиком вперёд не пишем:
таблицы появляются вместе с фичей, которая ими пользуется.

Правила:

1. Закончил шаг — сменил `[ ]` на `[x]` **в том же изменении**, что и код.
   Отдельного прохода «сейчас поотмечаю» не бывает.
2. Шаг считается сделанным, только когда написан код, проходят тесты по нему
   и обновлена документация из таблицы выше. Наполовину — это `[ ]`.
3. Этап закрывается только после проверки руками по строке «Можно потрогать».
   Зелёные тесты при неработающей странице этап не закрывают.
4. **Шаг, помеченный в плане `(вручную)`, делает пользователь, а не Claude.**
   Это внешние сервисы, ключи, загрузка файлов, замеры и скриншоты. Дошли
   до такого шага — останавливаемся и говорим, что именно нужно сделать.
   Обходить его заглушкой или выдумывать ключи нельзя.
5. Отмечен первый пункт этапа — статус этапа в таблице «Прогресс» становится 🟨,
   отмечены все — ✅.
6. Работа, которой в плане нет, сначала дописывается пунктом в нужный этап,
   потом делается. Молча — нельзя, иначе план перестаёт отражать реальность.
7. Расхождение с PRD — строка в «Открытые» в разделе «Расхождения с PRD»
   в конце плана, затем правка PRD, затем код.

## Порядок работы над фичей

Каждый этап из [docs/PLAN.md](docs/PLAN.md) проходит **две фазы**. Первая
заканчивается согласованием, вторая — рабочим кодом. Пропускать нельзя ни одну,
в том числе когда задача кажется очевидной.

### Фаза 1 — подготовка, до единой строки кода

1. **Ресерч.** Как это делается в Nuxt 4, NestJS 12, Prisma 7 и Nuxt UI 4
   **сейчас**. Какие библиотеки нужны, какие уже есть, чем отличаются. Опора —
   установленные скилы и официальная документация, а не память о старых статьях.
2. **План фичи** отдельным файлом `docs/features/F<N>-<краткое-имя>.md`
   по шаблону [docs/features/TEMPLATE.md](docs/features/TEMPLATE.md):
   принятые технические решения и **почему именно они**, библиотеки и версии,
   **примеры кода** по ключевым местам, список затрагиваемых файлов, что
   покрывается тестами, риски и открытые вопросы.
3. **Расхождение с PLAN.md выносится на обсуждение.** Ресерч показал, что
   записанное в плане решение неоптимально — **не реализовывать молча и не
   переписывать план втихую**. Обсудить, договориться, потом править PLAN.md
   (а если задета продуктовая часть — сначала PRD).
4. **Согласование.** План показывается целиком и ждёт **явного «добро»**.
   Без него реализация не начинается.

### Фаза 2 — реализация, после «добро»

1. **Ветка** `feat/<имя>` от актуального `main` — тот же префикс, что
   у типа коммита в Conventional Commits.
2. **Красные тесты.** Перед backend-кодом — e2e, перед frontend-кодом —
   модульные. Запустить и убедиться, что падают **по делу**.
3. **Реализация** по согласованному плану фичи.
4. **Зелёные тесты:** `test`, `test:e2e`, `lint`, `format:check`.
5. **Код-ревью скилом `/requesting-code-review`.**
6. **Исправления по ревью**, затем повторный прогон тестов.
7. **Проверка UI через Playwright MCP** — пройти в реальном браузере сценарий
   из строки «Можно потрогать». Нашлись проблемы — исправить и проверить снова.
   Пропускается только на этапах без интерфейса.
8. **Отметить сделанное** в PLAN.md и обновить документацию.

Планы фич после этапа не удаляются: через полгода это единственное место, где
записано, почему выбрана именно эта библиотека и именно это решение.

## Тесты пишутся до кода

**Сначала падающий тест, потом реализация.** Это правило проекта, а не пожелание:
тест, написанный после кода, проверяет то, что получилось, а не то, что требовалось.

| Что реализуем               | Что пишем первым                      | Где               |
| --------------------------- | ------------------------------------- | ----------------- |
| Эндпоинт, guard, транзакция | **e2e-тест** через Supertest          | `apps/api/test/`  |
| Компонент, страница, стор   | **модульный тест** на Testing Library | `apps/web/app/**` |

Цикл на каждый шаг плана:

1. **Написать тест** на требуемое поведение — по PRD, а не по будущей реализации.
2. **Запустить и убедиться, что он падает.** Красный тест обязателен: тест,
   зелёный до написания кода, не проверяет ничего. Упал не по той причине
   (опечатка, не поднялась база) — чинится до перехода дальше.
3. **Написать минимальную реализацию.**
4. **Запустить снова и убедиться, что он проходит** — вместе со всеми остальными.

```bash
npm run test:e2e -w @shop/api     # красный → пишем эндпоинт → зелёный
npm run test -w @shop/web         # красный → пишем компонент → зелёный
```

Шаг плана считается сделанным только после четвёртого пункта. «Тесты допишу
следующим шагом» — это невыполненный шаг, а не выполненный наполовину.

Исключения ровно два: разовые скрипты (сиды, миграции) и чистая вёрстка без
логики. Всё, у чего есть ветвление, права, деньги или остатки, — только через цикл.

## Node 24 обязателен

По умолчанию в shell стоит Node 20. **Перед любой командой npm:**

```bash
nvm use 24
```

В `package.json` прописан `"engines": { "node": ">=24" }`, на 20-й версии установка упадёт.

## Команды

Всё запускается **из корня**. В папку приложения заходить и ставить пакеты там не надо.

```bash
nvm use 24

npm run db:up          # Postgres 18 в Docker
npm run dev            # contracts (watch) + api :3001 + web :3000 разом

npm run build          # contracts → api → web, именно в этом порядке
npm run lint           # oxlint по воркспейсам
npm run test           # vitest по воркспейсам
npm run format         # prettier по всему репозиторию

npm run db:migrate     # prisma migrate dev
npm run db:seed
npm run db:studio
```

Установка пакета в конкретный воркспейс:

```bash
npm i <пакет> -w @shop/api     # или -w @shop/web, -w @shop/contracts
```

## Структура

```
apps/api        @shop/api        NestJS 12 (ESM) + Prisma 7 → :3001
apps/web        @shop/web        Nuxt 4 + Nuxt UI 4        → :3000
packages/contracts  @shop/contracts  схемы zod, общие для api и web
```

У `apps/api` и `apps/web` есть собственные `CLAUDE.md` — читать их при работе внутри.

## Порядок сборки

`@shop/contracts` компилируется в `dist/`, а `@shop/api` и `@shop/web` импортируют
именно собранный `dist`, не исходники. Поэтому:

- перед первой сборкой api или web нужен `npm run build -w @shop/contracts`;
- в разработке `npm run dev` держит contracts в watch-режиме, отдельно собирать не надо;
- изменил схему в contracts — жди пересборки, иначе увидишь старые типы.

## Контракты — единственный источник правды

Форма любого запроса и ответа описывается схемой zod в `packages/contracts` (PRD §9.4).

- API валидирует вход этой схемой.
- Фронт выводит из неё типы через `z.infer`.
- Дублировать типы руками в `apps/*` запрещено. Разошлись — виноват дубликат.

## Деньги

Все суммы в базе, в API и в контрактах — **целые центы** (`priceCents: 129900`).
Числа с плавающей точкой для денег не используются нигде.
Форматирование в `$1,299.00` — одной общей функцией из `@shop/contracts`, не руками.

## Prettier

Два разных конфига, это осознанно и менять не нужно:

| Где                    | Конфиг                 | Стиль                           |
| ---------------------- | ---------------------- | ------------------------------- |
| корень, web, contracts | `.prettierrc.json`     | без точек с запятой, ширина 100 |
| `apps/api`             | `apps/api/.prettierrc` | с точками с запятой, ширина 80  |

Prettier берёт ближайший конфиг вверх по дереву. `npm run format` из корня
раскладывает оба стиля правильно.

### Форматирование по хуку

В `.claude/settings.json` стоит хук `PostToolUse` на `Write|Edit`: после каждой
правки файла Claude Code прогоняет по нему Prettier. Руками `npm run format`
после каждого изменения запускать не нужно — только перед коммитом, чтобы
захватить файлы, которые правились не через Claude.

Хук молчит при успехе и никогда не блокирует работу. Посмотреть или выключить
его можно через `/hooks`.

**Prettier 3 по умолчанию читает `.gitignore`,** а не только `.prettierignore`.
Всё, что лежит в `.gitignore`, форматтер пропускает молча — и хук, и
`npm run format`, и `npm run format:check`. Сейчас под это попадает вся папка
`docs/`: она в `.gitignore`, поэтому документация форматируется только вручную
через `--ignore-path .prettierignore`.

## Безопасность

- `.env` **никогда** не коммитится. `.env.example` коммитится всегда, с пустыми значениями.
- Секреты для прода генерируются заново и не совпадают с локальными.
- Токены живут в httpOnly + Secure + SameSite=Lax куках. В `localStorage` — никогда.
- Пароли — argon2.
- Подпись вебхука Stripe проверяется всегда.
- Ключ Cloudinary в браузер не попадает: загрузка подписывается на сервере.
- `docker compose down -v` **удаляет базу**. Без `-v` — нет. Флаг ставить только осознанно.

## MCP

Подключён **Playwright MCP** — им проверяется UI в реальном браузере в конце
каждого этапа с интерфейсом (см. «Порядок работы над фичей», шаг 7).
Модульные тесты в jsdom не покажут съехавшую сетку, невидимый фокус
и ошибку в консоли — для этого и нужен проход браузером.
