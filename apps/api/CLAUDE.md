# @shop/api

NestJS 12 в режиме ESM + Prisma 7 + PostgreSQL. Порт 3001.

Общие правила репозитория — в [корневом CLAUDE.md](../../CLAUDE.md).
Требования к эндпоинтам — в [docs/PRD.md](../../docs/PRD.md), разделы 5, 6 и 9.

## ESM: расширение `.js` в импортах обязательно

`"type": "module"` + `"moduleResolution": "nodenext"`. Относительные импорты
пишутся **с расширением `.js`**, даже когда файл на самом деле `.ts`:

```ts
import { AppModule } from './app.module.js'; // ✅ так
import { AppModule } from './app.module'; //    ❌ упадёт в рантайме
```

Пакеты из `node_modules` импортируются как обычно, без расширения.

## Prisma 7 — четыре отличия от того, что пишут в старых статьях

**1. URL базы задаётся в `prisma7.config.ts`, а не в `schema.prisma`.**
В блоке `datasource db` остался только `provider`. Строку подключения CLI берёт
из конфига, а рантайм — из `DATABASE_URL` при создании клиента.

**2. `directUrl` больше не существует.** В Prisma 7 его удалили. Для Neon,
где нужен прямой (не пуловый) URL для миграций, разделение делается в конфиге:

```ts
datasource: {
  // Этот URL использует ТОЛЬКО CLI: migrate, db push, интроспекция.
  url: process.env['DIRECT_URL'] ?? process.env['DATABASE_URL'],
},
```

Рантайм при этом продолжает ходить через пул по `DATABASE_URL`.

**3. `migrate dev` больше не генерирует клиент.** После каждого изменения схемы:

```bash
npm run db:migrate     # из корня
npm run prisma:generate -w @shop/api
```

**4. Клиент генерируется в `src/generated/prisma`** (потому что в проекте есть `src/`),
и импортируется с `/client.js`:

```ts
import { PrismaClient } from './generated/prisma/client.js';
```

Папка `src/generated/prisma` в `.gitignore`. В `build` уже стоит `prisma generate`,
так что на сервере она появится сама.

## Тесты

### e2e-тест пишется до эндпоинта

Правило проекта (корневой `CLAUDE.md`, раздел «Тесты пишутся до кода»): **любой
backend-функционал начинается с e2e-теста**, а не заканчивается им.

Ещё раньше теста идёт фаза подготовки — ресерч, план фичи в `docs/features/`
и согласование с пользователем. Ни тест, ни тем более эндпоинт не пишутся,
пока плана нет и он не одобрен (корневой `CLAUDE.md`, «Порядок работы над фичей»).

```bash
npm run test:e2e -w @shop/api
```

1. Написал e2e на требуемое поведение — по PRD, а не по будущей реализации.
2. Запустил, **убедился, что он красный**. Зелёный до написания кода не проверяет
   ничего; упал не по той причине (не поднялась база, опечатка в маршруте) —
   чинится сразу.
3. Написал контроллер, сервис, guard.
4. Запустил снова — **зелёный**, и остальные тесты тоже.
5. Прогнал `/requesting-code-review` и починил найденное.

Модульные тесты (`*.spec.ts`) пишутся тем же циклом на чистую логику: расчёт
итогов, правила доставки, переходы статусов, проверки прав.

Шаг плана закрывается только после пункта 5. Сиды и миграции — исключение.

### Конфигурация

Vitest, не Jest. `globals: true`, поэтому `describe`/`it`/`expect` импортировать не нужно.

| Файлы                | Что                      | Конфиг                 |
| -------------------- | ------------------------ | ---------------------- |
| `src/**/*.spec.ts`   | модульные                | `vitest.config.ts`     |
| `test/*.e2e-spec.ts` | сквозные через Supertest | `vitest.config.e2e.ts` |

Сквозные тесты ходят в **отдельную базу** `DATABASE_URL_TEST`, а не в рабочую:
они чистят таблицы между тестами. `npm run test:e2e` сам создаёт базу
и накатывает миграции, так что на новой машине ничего делать руками не нужно.

Хелперы в `test/helpers/`: `createTestApp`, `resetState` (пустые таблицы +
сброшенный лимит частоты), регистрация и выдача токенов.

Что обязательно покрыто тестами (PRD §10):

- вход и обновление токена;
- создание заказа;
- **гонка за последним остатком**;
- идемпотентность вебхука Stripe;
- переходы статусов заказа и проверки прав.

Процент покрытия целью не является — целью является этот список.

## Линтер и формат

Линтер — **oxlint**, не ESLint. Конфиг `oxlint.json`.

Prettier здесь свой (`.prettierrc`): **с точками с запятой**, ширина 80. Это
отличается от корня и от `apps/web` — так и задумано, править не надо.

## Остаток товара — центральное место

PRD §9.2. Списание остатка выполняется **одним атомарным UPDATE с условием**,
а не «прочитали → проверили → записали»:

```sql
UPDATE "Product" SET stock = stock - $qty WHERE id = $id AND stock >= $qty
```

Ноль затронутых строк = товара не хватило, заказ не создаём. Проверка наличия
отдельным `SELECT` перед записью — ошибка: между чтением и записью влезет
другой запрос.

Заказ висит в `pending_payment` дольше 30 минут — фоновая задача отменяет его
и возвращает остаток.

## Правила эндпоинтов

- Вход валидируется схемой zod из `@shop/contracts`. Свои DTO рядом не создаём.
- Ответ по форме совпадает со схемой из контрактов.
- Ошибки — стандартные исключения Nest (`NotFoundException`, `ForbiddenException`
  и т. д.), не голые `throw new Error`.
- Каждый изменяющий эндпоинт админки закрыт **и** проверкой роли, **и** проверкой
  владения ресурсом, где это применимо.
- `admin` на странице для `super_admin` получает **403**, а не редирект.
- Ограничение частоты на `/auth/*` — 10 попыток в минуту с одного IP.
- Вебхук Stripe публичный, но подпись проверяется всегда и обработчик идемпотентен:
  Stripe доставляет событие по несколько раз.

## Что обновить вместе с кодом

Общее правило и полная таблица — в [корневом CLAUDE.md](../../CLAUDE.md).
Здесь то, что касается именно API:

| Изменение                                   | Что обновить                                                                |
| ------------------------------------------- | --------------------------------------------------------------------------- |
| Правка `prisma/schema.prisma`               | **план фичи** + миграция + `prisma generate` (сам он больше не запускается) |
| Новый или изменённый эндпоинт               | PRD §5–6 **и** схема zod в `packages/contracts`                             |
| Новая переменная окружения                  | `.env.example` **и** docs/DEPLOY.md, если она нужна на Render               |
| Новый скрипт в `package.json`               | «Команды» в корневом CLAUDE.md                                              |
| Изменились правила статусов, прав, остатков | PRD §5.7 / §9.2 + разделы «Остаток товара» и «Правила эндпоинтов» здесь     |

PRD §7 описывает **сущности предметной области**, а не колонки: имена таблиц
и полей туда не переносятся. Схема живёт в плане фичи, которая её вводит.

### Переменные окружения

| Переменная                | Зачем                                                                          | Нужна на проде |
| ------------------------- | ------------------------------------------------------------------------------ | -------------- |
| `DATABASE_URL`            | рабочая база                                                                   | да             |
| `DATABASE_URL_TEST`       | база для сквозных тестов, её чистят между тестами                              | нет            |
| `JWT_ACCESS_SECRET`       | подпись access-токена                                                          | да             |
| `JWT_REFRESH_SECRET`      | ключ HMAC для хеша refresh-токена                                              | да             |
| `WEB_ORIGIN`              | источник для CORS                                                              | да             |
| `PORT`                    | порт; на Render задаётся платформой                                            | нет            |
| `INTERNAL_REQUEST_SECRET` | общий с витриной; по нему API доверяет адресу посетителя из `x-client-address` | да             |
| `TRUST_PROXY`             | `1` только там, где перед приложением реально стоит прокси                     | да (Render)    |

`TRUST_PROXY=1` там, где прокси нет, — дыра: тогда `X-Forwarded-For` подделает
кто угодно и получит свежий счётчик лимита на каждый запрос. Локально `0`.
Без `INTERNAL_REQUEST_SECRET` в проде лимит на вход считался бы один на весь
магазин: браузер в API не ходит, все запросы приходят с адреса витрины.

`.env.example` — единственный способ узнать, какие переменные нужны проекту:
сам `.env` в git не попадает. Добавил переменную в `.env`, не добавив в
`.env.example`, — сломал сборку всем остальным, включая себя на новой машине.

## Раскладка `src/`

```
src/
  main.ts                  bootstrap, CORS, trust proxy, порт
  app.module.ts            корневой модуль, подключает остальные
  common/                  ZodValidationPipe, декоратор @CurrentUser
  prisma/                  PrismaModule (глобальный) + PrismaService
  users/                   поиск пользователя, toSessionUser
  auth/                    контроллер, сервисы, guard'ы
  health/                  GET /health для пробы Render
  generated/prisma/        клиент Prisma, в .gitignore
```

`toSessionUser` — единственное место, где строка базы превращается в ответ API.
Отдавать модель Prisma напрямую нельзя: в ней `passwordHash`.

Правило: **модуль на фичу**, папка на модуль, имя папки совпадает с именем
модуля. Пополняется вместе с этапами из [PLAN.md](../../docs/PLAN.md).
