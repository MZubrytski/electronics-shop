# @shop/web

Nuxt 4 + Nuxt UI 4. Порт 3000.

Общие правила репозитория — в [корневом CLAUDE.md](../../CLAUDE.md).
Требования к страницам — в [docs/PRD.md](../../docs/PRD.md), разделы 4 и 5.
**Все визуальные решения — в [docs/DESIGN.md](../../docs/DESIGN.md).** Палитру,
шрифт, шкалу и сетку оттуда не изобретаем заново.

**Перед вёрсткой любого блока открывается его карточка в
[дизайн-системе](https://claude.ai/artifact/HJHzHdZum16HeFoazKCFri).** Там лежат токены и
компоненты витрины — шапка, герой, плитка категории, промо-баннер, карточка
товара, бейджи, состояния списков — каждый с разметкой и правилами. В карточке
написано, что даёт потребитель и что нарушать нельзя; сверяться с ней нужно
до первой строки шаблона, а не после ревью.

## Nuxt 4: исходники лежат в `app/`

Главное отличие от Nuxt 3 и от большинства статей: `srcDir` теперь `app/`.

```
apps/web/
  app/               ← сюда пишем весь фронтенд, это srcDir
    app.vue
    app.config.ts
    assets/css/main.css
    pages/           ← страницы здесь, НЕ в apps/web/pages
    components/      ← автоимпорт по имени: components/ui/Input.vue → <UiInput />
    composables/     ← автоимпорт, только файлы верхнего уровня
    utils/           ← автоимпорт чистых функций
    layouts/
    middleware/      ← навигационные guard'ы браузера
    plugins/         ← session.server.ts наполняет сессию до первого байта
    stores/          ← Pinia, автоимпорт useXStore
  server/            ← а вот server остаётся в корне приложения, вне app/
    middleware/      ← выполняется на каждый запрос: разбор и продление сессии
    api/             ← маршруты, к которым ходит браузер
    utils/           ← автоимпорт внутри server/
  public/
  nuxt.config.ts
```

Ошибиться уровнем легко: `apps/web/pages/` Nuxt просто не увидит.

Алиасы Nuxt 4: `~` и `@` указывают на `app/`, `~~` и `@@` — на корень
приложения, `#shared` — на `shared/`.

**Папки заводятся вместе с кодом, который в них лежит.** Пустых каталогов
«на будущее» не держим: git их всё равно не отслеживает, а в дереве выше они
только мешают.

### Автоимпорт, а не относительные пути

Компоненты, композаблы, утилиты из `app/utils/` и Pinia-сторы импортируются
сами. Писать `import { useSessionStore } from '../stores/session'` не нужно —
и вредно: путь ломается при переносе файла.

Исключение — тесты: там импорт явный, потому что компонент монтируется вне
приложения Nuxt.

### Про `shared/` в Nuxt

Nuxt 4 даёт корневую папку `shared/` для кода, который автоимпортируется
и в `app/`, и в `server/`. **Мы её не заводим:** эту роль в монорепозитории
играет `@shop/contracts` — схемы, типы и форматирование денег лежат там и
доступны обоим приложениям и API. Две «общие» папки разойдутся.

## Маршрутизация

`app.vue` содержит `<UApp>` → `<NuxtLayout>` → `<NuxtPage />`. `<UApp>` —
обязательная обёртка Nuxt UI: без неё не работают тосты, тултипы и оверлеи.

Сессия наполняется **серверным плагином** `app/plugins/session.server.ts`
до первого байта HTML. Без него страница отрисовалась бы гостевой и мигнула
бы при гидратации — ровно то, ради чего выбирались куки.

## Nuxt UI

Подробности API компонентов — в скиле `nuxt-ui` и через MCP-сервер Nuxt UI.
Здесь только то, что относится к этому проекту:

- **Иконки** — набор `lucide`, он уже установлен: `i-lucide-shopping-cart`.
  Эмодзи вместо иконок не используем.
- **Только семантические цвета:** `text-muted`, `bg-elevated`, `border-default`.
  Сырые классы Tailwind вроде `text-gray-500` ломают тему — запрещены.
- **`text-dimmed` для читаемого текста запрещён** — на палитре `slate` это
  `slate-400`, контраст 2.63:1, WCAG AA не проходит. Таблица — DESIGN.md §4.
- **`text-muted` не ставится на `bg-brand-subtle`** — 4.37:1, порог не проходит.
  Там берётся `text-toned`.
- Своего компонента рейтинга в Nuxt UI нет — звёзды пишем сами на `UIcon`.
- Настройки темы: цвета в `app/app.config.ts`, палитра `brand`, шрифт и радиус
  в `app/assets/css/main.css`.
- **`main.css` переопределяет `--ui-success`, `--ui-warning`, `--ui-error`
  и `--ui-info`.** Nuxt UI подставляет в них ступень 500, а она на белом не
  проходит порог контраста как цвет текста (DESIGN.md §4). Правка живёт
  в одном месте — не дублируйте её классами по компонентам.
- **Тёмная тема выключена** в `nuxt.config.ts`, пока её нет в дизайн-системе
  (DESIGN.md §22). Классы `dark:` писать рано.

## Данные и авторизация

**Куки выставляет витрина, а не API.** Правило: куками распоряжается тот, кто
владеет адресом, на который ходит браузер, — а это `apps/web`. API кук не видит
вовсе, он принимает токен заголовком. Почему именно так и что ломается иначе —
в [SESSIONS-EXPLAINED.md](../../docs/SESSIONS-EXPLAINED.md).

Токены живут в **httpOnly-куках**, поэтому браузер не может читать их из JS.
Отсюда правило:

- Запросы, которым нужна авторизация, идут **через свои серверные маршруты**
  в `server/api/*`. Они читают куку и передают API токен заголовком —
  не пробрасывают куку дальше.
- Сессия разбирается один раз за запрос в `server/middleware/session.ts`
  и кладётся в `event.context.session`. Продление живёт там же: только куки,
  выставленные на настоящем входящем запросе, доезжают до браузера.
- Обращаться из браузера напрямую в API по `NUXT_API_URL` для таких запросов нельзя.
- `useFetch` на странице с SSR должен корректно передавать заголовки — иначе
  на сервере запрос уйдёт без куки и вернёт 401.

## Переменные окружения

Nuxt связывает их с `runtimeConfig` по имени автоматически:

| Переменная                     | Куда попадает                         | Видна браузеру |
| ------------------------------ | ------------------------------------- | -------------- |
| `NUXT_API_URL`                 | `runtimeConfig.apiUrl`                | нет            |
| `NUXT_INTERNAL_REQUEST_SECRET` | `runtimeConfig.internalRequestSecret` | нет            |

Значение `NUXT_INTERNAL_REQUEST_SECRET` должно совпадать с `INTERNAL_REQUEST_SECRET`
в `apps/api`: по нему API доверяет адресу посетителя, который витрина шлёт
в `x-client-address`. Разошлись — лимит на вход считается один на весь магазин.
| `NUXT_PUBLIC_SITE_URL` | `runtimeConfig.public.siteUrl` | да |

Всё, что попадает в `public`, уезжает в браузер. Секретам там не место.

| Маршруты                          | Режим        | Почему                                    |
| --------------------------------- | ------------ | ----------------------------------------- |
| `/`, `/catalog`, `/product/:slug` | SSR          | нужны для SEO (PRD §10)                   |
| `/admin/**`                       | `ssr: false` | закрытая часть, задано в `nuxt.config.ts` |
| `/checkout`, `/account/**`        | клиент       | приватные данные                          |

## Состояние фильтров — в URL

Фильтры, сортировка и страница каталога живут **в query-параметрах** (PRD §5.1).
Не в Pinia, не в `localStorage`. Ссылку должно быть можно переслать, а перезагрузка
не должна сбрасывать выбор.

## Каждый список рисуется в четырёх состояниях

Загрузка (скелетоны, не спиннер), пусто, ошибка, данные. Пустое состояние
всегда с кнопкой действия. Подробности и тексты — DESIGN.md §15 и карточки
`LoadingSkeleton`, `EmptyState`, `ErrorState` в дизайн-системе.

## Модульный тест пишется до компонента

Правило проекта (корневой [CLAUDE.md](../../CLAUDE.md), раздел «Тесты пишутся
до кода»): **любой фронтенд-функционал начинается с модульного теста** на
Testing Library, а не заканчивается им.

Ещё раньше теста идёт фаза подготовки — ресерч, план фичи в `docs/features/`
и согласование с пользователем. Ни тест, ни тем более компонент не пишутся,
пока плана нет и он не одобрен («Порядок работы над фичей» в корневом файле).

```bash
npm run test -w @shop/web
```

1. Написал тест на требуемое поведение — что видит пользователь и что происходит
   после клика, а не какие внутри вызовы.
2. Запустил, **убедился, что он красный**. Компонента ещё нет — тест падает
   на импорте или на отсутствующем элементе, и это правильное красное.
3. Написал компонент, страницу или стор.
4. Запустил снова — **зелёный**, и остальные тесты тоже.

Что тестируем: фильтры каталога, корзину, валидацию формы оформления, состояния
списков, поведение при отсутствии прав (PRD §10). Что не тестируем: чистую
вёрстку без логики — там проверять нечего.

## Модульных тестов мало: UI проверяется в браузере

Testing Library монтирует компонент в jsdom. Она не покажет съехавшую сетку,
невидимый фокус, неработающий скролл и ошибку в консоли на реальной странице.
Поэтому **у каждого этапа с интерфейсом есть отдельный шаг — проход через
Playwright MCP**:

1. Поднять приложение (`npm run dev`).
2. Пройти в браузере сценарий из строки «Можно потрогать» соответствующего
   этапа [docs/PLAN.md](../../docs/PLAN.md) — именно его, а не произвольный клик.
3. Проверить консоль на ошибки и предупреждения.
4. Нашлись проблемы — исправить и пройти сценарий заново.

Порядок в конце этапа: зелёные тесты → `/requesting-code-review` → правки →
**Playwright MCP** → правки. Этап закрывается после этого, а не после зелёных
модульных тестов.

## Чего здесь нет

- **Нет проверки типов, и это решение, а не недоделка.** Скрипта `typecheck`
  здесь не заведено, CI её не гоняет, требование снято из PRD §11 решением
  от 12.09.2026. Захочется добавить — это отдельная задача вместе с `vue-tsc`.
- **Нет `@nuxt/image`.** Для Cloudinary его нужно будет поставить отдельно.

## Что обновить вместе с кодом

Общее правило и полная таблица — в [корневом CLAUDE.md](../../CLAUDE.md).
Здесь то, что касается именно фронтенда:

| Изменение                                | Что обновить                                                   |
| ---------------------------------------- | -------------------------------------------------------------- |
| Новая страница                           | Карта страниц PRD §4 **и** таблица «Рендеринг» выше            |
| Изменился режим рендеринга маршрута      | таблица «Рендеринг» выше + `routeRules` в `nuxt.config.ts`     |
| Палитра, шрифт, радиус, сетка, состояния | docs/DESIGN.md + дизайн-система — решения живут там, не в коде |
| Новый или изменённый блок витрины        | карточка компонента в дизайн-системе                           |
| Новая переменная окружения               | `.env.example` + таблица «Переменные окружения» выше           |
| Новая папка в `app/`                     | дерево в разделе «Nuxt 4: исходники лежат в `app/`»            |

Два раздела здесь устаревают в первую очередь — за ними следить особенно:

- **«Маршрутизация ещё не включена»** — как только появится `app/pages/`,
  раздел надо переписать: он описывает временное состояние.
- **«Чего здесь нет»** — поставил `@nuxt/image`, завёл `typecheck` или первый
  тест, вычеркни соответствующий пункт. Список неправды хуже отсутствия списка.
